# 集め直し方式（Gather、試作）

記録日: 2026-11-01

内蔵GPUでは点群描画が頂点処理で詰まっており、Direct描画は1点を4頂点・三角形2枚のQuadで描いています。集め直し方式は、点を1頂点の1画素点で描き、円の形は画面上で作り直します。

1. 全点を1画素の点として作業テクスチャへ描き、1画素に最も手前の1点だけを残します（色・画面半径・深度）。
2. computeシェーダで、各画素の周り半径4画素の点を調べ、自分を覆う円のうち最も手前の点の色と深度を作業テクスチャへ書きます。8x8画素の区画と周り4画素を共有メモリへ1回だけ読み込み、テクスチャ読み込みを減らしています。
3. 全画面パスで、その結果をカメラの色と深度へ書き写します。円に覆われない画素は書きません。
4. ノード中心での画面半径が4画素を超えるノード（周回中の点の約10%）は、これまで通りQuadで描きます。

主なファイル:

- `Assets/PointCloudViewer/Script/Opc/GatherRender/OpcGatherRenderFeature.cs`: 点描き → 集め直し → 書き写しのパスを積むURP Renderer Featureです。`_useComputeResolve` をオフにすると、集め直しを全画面のフラグメントシェーダで行う版に切り替わります。
- `Assets/PointCloudViewer/Shader/PointCloud_GatherFill.shader`: 1画素の点を描き、色と画面半径を詰めた値・深度を出力します。
- `Assets/PointCloudViewer/Shader/PointCloudGatherResolve.compute`: 共有メモリを使った集め直しです。
- `Assets/PointCloudViewer/Shader/PointCloud_GatherComposite.shader`: 集め直しの結果をカメラへ書き写します。
- `Assets/PointCloudViewer/Script/Opc/MultiDrawRenderer.cs`: 円が大きいノードのコマンドを先頭へ集め、その範囲だけQuadで描きます。

計測日: 2026-11-01、Unityエディタ上、`CameraOrbitMover` + `BenchmarkSession (capture=60fps)`、570フレーム、1920x1080、内蔵GPU（Intel UHD、D3D11）。モードを交互に各2回計測しました。

| モード | 平均フレーム時間 | メモ |
| --- | ---: | --- |
| Direct | 24.6 / 26.7 ms | Quadで円を描く |
| Gather（大きい円はQuad） | 18.7 / 17.9 ms | Quadで描く点は平均約44万点（全体の約10%） |
| Gather（全点を集め直し、半径4で切る） | 16.9 / 17.4 ms | 2026-11-01の別の回。Directは27.6 / 26.6 ms |
| Gather（フラグメント版の集め直し） | 22.4 / 22.6 ms | 同上 |
| DirectPixelPoints（比較用、全点1画素） | 11.4〜11.6 ms | 円を作らないため手前の面が透け、見た目は別物 |

後の回（SSAOの計測、[フレーム時間の原因分析](profiler-frame-analysis.md#点群以外の固定費)）では、Gather（大きい円はQuad）が16.24 / 16.24 ms、同じ回のDirectが25.53 msでした。上の表の18.7 / 17.9 msより約2ms速く、理由は確認していません。

ビルドでの計測（2026-11-02、Windowsプレイヤー・通常ビルド・D3D11・Intel UHD、`Tools/Run-Benchmark.ps1`、1920x1080の窓、コミット 310e1b7）: Direct → Split → DirectPixelPoints → Gather の順に4回測りました。

| モード | 平均フレーム時間 | p95 |
| --- | ---: | ---: |
| Direct | 24.25 / 24.19 / 24.20 / 24.23 ms | 27.0〜27.3 ms |
| Gather（大きい円はQuad） | 15.26 / 15.21 / 15.21 / 15.18 ms | 17.2〜17.8 ms |
| DirectPixelPoints（比較用） | 10.52 / 10.42 / 10.41 / 10.47 ms | 12.7〜12.8 ms |

- ビルドではGatherがDirectより約9.0ms（約37%）速く、エディタでの差（約6〜9ms）と同じ程度です。
- Quadで描く点は平均約45万点で、エディタと同じ程度です。
- 4回目の計測中に画面を撮り、点群が描かれていることを確認しました。

見た目: 静止画（1280x720のキャプチャ）でDirectと色が8段階より大きく違う画素は9.0%でした。街全体を見た目視ではほぼ同じですが、原寸で拡大すると手前の建物で円が切れて隙間が出ます（[静止時の画素差（原寸）](#静止時の画素差原寸)）。

### 静止時の画素差（原寸）

記録日: 2026-11-02、コミット 20818f5

条件: Splitの[静止時の画素差](split-render-validation.md#静止時の画素差)と同じです。Unityエディタ、Play中、Intel UHD・D3D11、ゲーム画面1920x1080、`sample.opc`、`ScreenCapture.CaptureScreenshot` で原寸撮影、SSAOあり。画素ごとにRGBの差の最大値を見ています。視点の移動は、初期視点から右下の建物（画面の (1450, 950)）へ向かう方向です。

| 比べたもの | 少しでも違う | 差 > 8 | 差 > 32 |
| --- | ---: | ---: | ---: |
| Direct と Direct（初期視点、離れた時刻で2枚） | 0% | 0% | 0% |
| Gather と Gather（同上） | 0% | 0% | 0% |
| Direct と Gather（初期視点、2組とも同じ値） | 15.01% | 8.50% | 3.00% |
| Direct と Gather（25単位移動） | 15.02% | 8.55% | 3.02% |
| Direct と Gather（50単位移動） | 13.85% | 8.23% | 2.98% |
| Direct と Gather（80単位移動） | 12.04% | 6.95% | 2.33% |

- 同じ条件のSplitは 1.56% / 0.73% / 0.22% で、Gatherの差はSplitの10倍以上です。9.0%は縮小のせいではありませんでした。
- **円が切れて隙間が出ます。** 初期視点の右下の建物で、Directの円は直径約15画素、Gatherの円は約9画素（半径4画素で切れた大きさ）で、円の間に奥が見えます。80単位移動の視点では、同じ建物でQuadで描かれたノードの円はDirectと同じ大きさで、隣のノードの円だけが小さく、ノードの境で大きさが変わります。
- 差 > 8 の画素を、つながった塊の大きさで分けると、初期視点では16画素以下の小さな塊が77.9%、257画素以上の大きな塊（上の切れた建物など）が14.0%です。
- 小さな塊が画面全体に散らばる主な原因は、円の中心を画素の中心へ丸めることでした（[細かい差の原因](#細かい差の原因円の中心の丸め)）。
- 円の境目の前後の違いだけ、という以前の説明は誤りでした。
- 80単位移動でも街全体が見える距離で、建物の目の前の視点は確認していません。

カメラ移動中の見た目（2026-11-01、エディタ）: 周回経路上を1フレーム0.6°ずつ進めた26視点で、視点ごとにDirectとGatherを撮り比べました。

- Directと違う画素は全視点で13.7〜13.9%で、視点によって増えません。
- 瞬き（相手のモードは前後の視点で安定しているのに、自分だけ前後と違う画素）は、Gather 0.335%、Direct 0.328%で同程度です。
- 連続4視点を拡大して見ても、目立つ違いはありません。
- 撮影の注意: ベンチマークを使わないPlayでは `Application.runInBackground` が無効で、エディタが裏にあると止まり、撮影が1つ前の画面を返します。撮影前に `Application.runInBackground = true` にしました。それでも最後の4視点は撮影がずれたため除いています（原因は未調査）。

制限:

- 1データ・1経路・1台のGPU（Intel UHD）だけの計測です。
- パスごとのGPU時間は取れていません。集め直しの重さは、半径を変えた時のフレーム時間の差から見積もっています（フラグメント版で半径4が約9ms）。
- 円が大きいノードの判定はノード中心の奥行きで行うため、同じノード内でカメラに近い点の円は半径4画素で切れることがあります。初期視点の手前の建物でも切れて隙間が出ることを確認しました（[静止時の画素差（原寸）](#静止時の画素差原寸)）。
- 集め直しの半径（4画素）は、`OpcLoader.GatherRadiusPixels` と2つのシェーダの `GATHER_RADIUS` で揃える必要があります。

## 円切れの対策: 手前の角で判定する（GatherNearDepthモード）

記録日: 2026-11-02

仮説: 「大きい円のノード」の判定を、ノード中心の奥行きからノードのいちばん手前の角の奥行きに変えると、ノード内のどの点も半径4画素を超えなくなり、円は切れない。その分Quadで描く点が増えて遅くなる。

予測:

- 見た目: 右下の建物の切れと隙間が消える。差 > 8 は8.50%から4〜7%へ減る（小さな塊の差は残る）
- 速度: Quadで描く点が全体の約半分になり、Gather（ビルド15.2 ms）とDirect（24.2 ms）の間、約20 msになる

判定基準:

- 見た目: 初期視点と80単位移動の視点で、円の切れ・隙間・ノード境の大きさの段差が見えないこと
- 速度: Split（ビルド20.7 ms）より速いこと。遅ければ、Splitに対する利点が無いので別の案を考える

結果（未コミットの作業中のコード、コミット 20818f5 に変更を加えた状態）:

見た目（条件は[静止時の画素差（原寸）](#静止時の画素差原寸)と同じ）:

| Directとの差 | 少しでも違う | 差 > 8 | 差 > 32 |
| --- | ---: | ---: | ---: |
| Gather（初期視点） | 15.01% | 8.50% | 3.00% |
| GatherNearDepth（初期視点） | 6.46% | 4.04% | 1.45% |
| Gather（80単位移動） | 12.04% | 6.95% | 2.33% |
| GatherNearDepth（80単位移動） | 5.67% | 3.43% | 1.21% |

- 拡大して見ると、両方の視点で右下の建物の円の切れ・隙間・ノード境の大きさの段差は消えました。判定基準を満たします。
- 差 > 8 は予測の4〜7%の下端です。それでも同じ条件のSplit（0.73%）の約5倍あります。

速度（エディタ、`CameraOrbitMover` + `BenchmarkSession (capture=60fps)`、570フレーム、1920x1080、Intel UHD・D3D11、`sample.opc`。Direct → Split → Gather → GatherNearDepth → GatherNearDepth → Gather → Split → Direct の順に測定）:

| モード | 平均フレーム時間 | Quadで描く点（平均） |
| --- | ---: | ---: |
| Direct | 25.20 / 25.11 ms | 全点（約429万点） |
| Split | 22.84 / 22.90 ms | なし |
| Gather | 16.14 / 16.36 ms | 約44万点（約10%） |

- GatherNearDepthはGatherより約4.3ms遅く、Splitより約2.3ms速いです。Gatherの速さの多くは、切れを許していた分でした。

ビルドでの速度（2026-11-03、Windowsプレイヤー・通常ビルド・D3D11・Intel UHD、`Tools/Run-Benchmark.ps1`、1920x1080の窓、コミット 20818f5 に未コミットの変更を加えた状態）: Direct → Split → Gather → GatherNearDepth の順に3周測りました。

- GatherNearDepthはSplitより平均で約1.3ms（約6%）速く、速度の判定基準を満たします。p95はSplitとほぼ同じです。
- Quadで描く点は平均約183万点（全体の約43%）で、エディタと同じ程度です。
- 別の回の計測中に窓の中身を撮り（`PrintWindow`）、点群が描かれていることを確認しました。

カメラ移動中の見た目（2026-11-03、エディタ、1920x1080を原寸で撮影）: 周回経路上（半径100、高さ50、中心を見る）を0.6°ずつ進めた26視点を、モードごとに撮りました。Gatherの以前の記録（1280x720）とは撮影条件が違うので、値は比べません。

| モード | Directとの差 > 8（26視点の平均） | 瞬き（24視点の平均） | 同じ組のDirectの瞬き |
| --- | ---: | ---: | ---: |
| Gather | 9.67% | 0.590% | 0.536% |
| GatherNearDepth | 8.71% | 0.517% | 0.462% |

- この経路はカメラが遠く、Directとの差はGatherとあまり変わりません。初期視点の4.04%は、手前の建物の割合が多い視点の値です。遠くの細かい差は、GatherNearDepthでは減りません。
- 同じ経路のSplitは測っていないので、Splitとの正確さの比較は初期視点の値（0.73%）だけです。

## 細かい差の原因（円の中心の丸め）

記録日: 2026-11-03、コミット c08e844 に一時的なシェーダ変更を加えて測定（変更はコミットしていません）

仮説: GatherNearDepthに残るDirectとの差の大部分は、Gatherが円の中心を画素の中心へ丸めることから来る。Directの円も同じ規則で丸めれば、差 > 8 は0.5%未満になる。

方法: `PointCloud_Circle.shader` に一時的な切り替えを入れ、円の中心を丸めました。GatherNearDepthのQuad部分も同じシェーダなので、両方に同じ丸めがかかります。条件は[静止時の画素差（原寸）](#静止時の画素差原寸)と同じで、視点は初期視点と周回経路上の6°です。

| 比べたもの | 初期視点 差 > 8 | 周回経路 差 > 8 |
| --- | ---: | ---: |
| Direct と GatherNearDepth（丸めなし） | 4.04% | 8.85% |
| Direct と GatherNearDepth（両方の中心を丸める） | 0.38% | 0.72% |
| Direct と GatherNearDepth（中心に加えて半径も1/16画素へ丸める） | 0.32% | 0.44% |
| 参考: Directの丸めなし と Directの中心を丸めたもの | 7.19% | 9.71% |

- 仮説の通りでした。差 > 8 の約92〜95%は、中心と半径の丸めで説明できます。
- これは描画の誤りではなく精度の差です。Gatherの円は、本来の位置から最大で約0.7画素（縦横0.5画素ずつ）ずれます。Splitは点ごとにワールド座標を保つので、このずれがありません。Directとの差がSplitより大きいのはこのためと考えられます。
- 残りの0.32〜0.44%の原因は確かめていません。1画素1点に絞ることで、半径の違うノードの円が消える影響を考えています（推測）。
- 同じ視点の2枚を比べていないので、この表のGatherNearDepthの再現性は確かめていません。Gatherでは、同じ視点の2枚の差は0%でした。
